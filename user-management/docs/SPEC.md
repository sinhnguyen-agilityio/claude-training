# User Management Dashboard — Specification

Status: **v1.1 draft** · Owner: Sinh Nguyen

## 1. Purpose

A small single-page app where an operator manages users (list, search, create, view, edit,
delete). It is a training project: the scope is deliberately small and there is no real
backend.

## 2. Architecture decisions

| Decision     | Choice                                             | Reason                                                                                                               |
| ------------ | -------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------- |
| Backend      | None. A mock REST API (MSW) runs in the browser.   | Scope is front-end only. The UI still makes real `fetch` calls, so swapping in a real API later needs no UI changes. |
| Persistence  | `localStorage`, behind a repository module         | Data survives reloads. SQLite was considered and dropped because it needs a server.                                  |
| Validation   | One Zod schema shared by the form and the mock API | The client and the "server" can never disagree on the rules.                                                         |
| Auth         | Out of scope                                       | Keeps the scope small.                                                                                               |
| Mock in prod | MSW runs in every build, including production      | There is no real backend, so the mock _is_ the API (and `pnpm e2e` runs against the production build).               |

## 3. Data model — `User`

| Field       | Type                              | Rules                                                                                                                                       |
| ----------- | --------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------- |
| `id`        | string (UUID)                     | Generated by the API                                                                                                                        |
| `firstName` | string                            | Required, trimmed, 1–50 chars                                                                                                               |
| `lastName`  | string                            | Required, trimmed, 1–50 chars                                                                                                               |
| `email`     | string                            | Required, valid email, trimmed and stored lowercase, **unique** case-insensitively (409 if taken; keeping your own email is not a conflict) |
| `phone`     | string \| null                    | Optional; digits, spaces, `+`, `-`, `()`; 7–20 chars counted as typed (formatting included); empty input is stored as `null`                |
| `role`      | `'admin' \| 'editor' \| 'viewer'` | Required. A label only (no permissions, since there is no auth)                                                                             |
| `status`    | `'active' \| 'inactive'`          | Required, default `active`                                                                                                                  |
| `createdAt` | ISO 8601 string                   | Set by the API                                                                                                                              |
| `updatedAt` | ISO 8601 string                   | Set by the API on every update                                                                                                              |

## 4. Mock API contract

| Method   | Path             | Success                               | Errors                    |
| -------- | ---------------- | ------------------------------------- | ------------------------- |
| `GET`    | `/api/users`     | 200 `{ data, total, page, pageSize }` | 400 invalid query         |
| `GET`    | `/api/users/:id` | 200 `User`                            | 404                       |
| `POST`   | `/api/users`     | 201 `User`                            | 400 validation, 409 email |
| `PATCH`  | `/api/users/:id` | 200 `User`                            | 400, 404, 409             |
| `DELETE` | `/api/users/:id` | 204                                   | 404                       |
| `POST`   | `/api/reset`     | 204                                   | —                         |

`GET /api/users` query params: `q` (search text, case-insensitive), `role`, `status`,
`sort` (`name` \| `createdAt`), `order` (`asc` \| `desc`), `page` (1-based), `pageSize`
(default 10, max 50). Defaults when absent: `sort=createdAt`, `order=desc`, `page=1`.

- `q` matches first name, last name or email, each field separately (so `john d` does not match
  "John Doe").
- Sorting by `name` orders by last name, then first name.
- Invalid values return 400: `pageSize` above 50, `page` below 1, or an unknown `role`, `status`,
  `sort` or `order`. A `page` past the end returns 200 with empty `data`.

Error body: `{ message: string, fieldErrors?: Record<string, string> }`.

On first load the API seeds a fixed set of 25 users (hard-coded, so tests can rely on exact
values). `POST /api/reset` restores the seed data. Every mock response has a small fixed delay
(~300 ms) so loading states are visible; tests wait on content, never on fixed timeouts.

## 5. Features and acceptance criteria

### F1 — List users (`/users`)

- Table columns: name, email, role, status, created date (locale format, e.g. "Oct 14, 2026"),
  and row actions (view / edit / delete). On narrow screens the table scrolls horizontally in its
  own container.
- **Given** users exist **When** I type in search **Then** after 300 ms the list shows only users
  whose first name, last name or email contains the text (case-insensitive).
- Role and status filters, and sort by name (last, then first) or created date (asc/desc).
  Default: newest first.
- Pagination at 10 per page, showing "Showing X–Y of Z".
- Search, filters, sort and page are kept in the URL, so reloading or sharing the link restores
  the same view. A `page` past the end redirects (replace) to the last page.
- Loading skeleton, empty state ("No users match your filters" + clear button), and an error
  state with a retry button.

### F2 — Create user (`/users/new`)

- Form fields follow §3. Errors show inline after blur or submit.
- **Given** the email already exists **When** I submit **Then** the email field shows "Email is
  already in use" and the form keeps my input.
- On success: a toast "User created" and I'm taken to the list.

### F3 — View user (`/users/:id`)

- Shows all fields, including created and updated date-times, with Edit and Delete actions.
- **Given** an unknown id **Then** a "User not found" state links back to the list.

### F4 — Edit user (`/users/:id/edit`)

- Same form as F2, pre-filled with the user's data. Submit is disabled until a value differs from
  the saved one (reverting a change disables it again).
- **Given** unsaved changes **When** I navigate away in the app, reload, or close the tab **Then**
  I'm asked to confirm.
- **Given** the new email is taken **When** I submit **Then** the same inline error as F2 shows.
- On success: a toast "User updated" and I'm taken to the detail page.

### F5 — Delete user

- From the list or the detail page, a confirmation dialog names the user.
- **When** I confirm **Then** the user is removed, a toast "User deleted" appears, and the list
  refreshes. If the current page becomes empty, the list goes back one page.
- Deleting from the detail page returns to the list with the last-used filters (or `/users`).

### F6 — Reset demo data

- A header button restores the seed data after a confirmation, then shows a toast "Demo data
  reset", clears cached data and goes to `/users` (page 1, no filters).

## 6. Non-functional requirements

- Accessible: semantic HTML, labelled inputs, keyboard-operable dialogs, focus management.
- Responsive down to 375 px wide.
- TypeScript strict mode. No `any` in app code.
- Unit/component coverage ≥ 80%. Each feature has at least one Playwright E2E journey.

## 7. Out of scope

Authentication and permissions, a real backend, bulk actions, import/export, i18n, avatars.
